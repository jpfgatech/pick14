# Parsing: basic Q snapshot study (instructions/03-1.md)

## Snapshot types and timing

Snapshots are taken AFTER the corresponding action, so the key encodes the
resulting state and characterises Q(action).

  A   — after match/pass (and DRAW1 if matched); state.phase is now PLAY
  B1  — after play in a pass turn (DRAW2 already applied); next player's MATCH
  B2  — after play in a match turn; next player's MATCH

Key vector = (snap_type_code, hand_digit_counts[13], pub_digit_counts[13])
  → 27 integers, used directly as a Python tuple dict key (collision-free)
  → digit index i corresponds to game_value = i+1  (jokers count toward digit 5)

## Outcome metrics

For each snapshot at player p's match-turn index j, collect outcomes at
player p's own subsequent match turns j+1 and j+2:

  mopt_k  : number of legal match options at the START of turn j+k
  mcat_k  : number of distinct match digit-categories at the START of turn j+k
             (category = sorted tuple of game-values used: pub + hand cards)
  pts_k   : points scored by p on turn j+k  (0 if pass)
  gap_k   : pts[p, j+k] − mean_q(pts[q, j+k])
             same future turn index across players, matching the instruction's
             example of 9/5/4 points in a 3-player round → gaps 3/-1/-2.

Horizon H1: (mopt_1, mcat_1, pts_1, gap_1)
Horizon H2: (mopt_1+mopt_2, mcat_1+mcat_2, pts_1+pts_2, gap_1+gap_2)

H2 sums both turns so that match-options and points accumulate, and the gap
represents the total relative-scoring improvement over two turns.

## Match categories explained

A legal match uses one public card (digit d_pub) and ≥1 hand cards
(digits d_h1, d_h2, …) such that d_pub + Σd_hi = 14.

Category = tuple(sorted([d_pub, d_h1, …]))

Multiple suit combinations of the same digit combo → one category
(the player always picks the highest-point suite version, so the digit
combo is the strategic unit of choice).

Different digit combos (e.g. A+5+8 vs 6+8) → different categories even if
they share a public card.  Categories represent distinct strategic choices.

## Analysis plan

Two independent 10k batches → merged 20k aggregate DB.

Implementation is split at a trace boundary:

1. `simulate_game_trace()` only steps the engine and records compact turn
   records plus post-action snapshot anchors. It does not aggregate, plot, or
   write files.
2. `add_trace_to_accumulators()` converts a finished trace into H1/H2 outcome
   samples.
3. Plotting and saving consume only the aggregated arrays.

1. Density: sorted sample-count curve (log y) for all-20k, batch-1, batch-2.
2. Metric curves: for each of {mopt, mcat, pts, gap}:
     - per-key mean ± std, x sorted by sample count (descending)
     - per-key mean ± std, x sorted by mean gap (ascending)
   Two sets: H2 and H1 separately.
3. Correlations (Pearson + Spearman) of per-key means for [mopt, mcat, pts, gap].
   Two sets: H2 and H1.
