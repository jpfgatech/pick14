# Parsing: 04 Decision-tree size and timing

## Goal

Measure how large the game decision tree actually is for a single fixed-deck
game, and how adding per-checkpoint deck reshuffles (a chance-node model) scales
the tree further.  All analysis is in `scripts/04_decision_tree.py`.

## Design

### Fixed-deck DFS (Part 1)

- A **fixed RNG seed** produces a fixed deck order.  Draws (DRAW1, DRAW2) are
  deterministic functions of the deck; they are resolved inline — no branching.
- The only branching is over **player decisions**: legal moves at MATCH and PLAY
  phases.
- At each game state:
  1. Resolve forced steps (`skip_empty_hands`, DRAW1, DRAW2) in-place.
  2. Enumerate `legal_moves(state)`.
  3. If 1 move: forced — apply and continue (no copy, no checkpoint).
  4. If ≥ 2 moves: **checkpoint** — `clone_state` for each branch and recurse.
- **Node limit** (default 200,000) halts the search early to prevent OOM/timeout.

#### Decision vs checkpoint

| Phase | Legal moves | Checkpoint? |
|-------|-------------|-------------|
| MATCH, 0 legal matches | 1 (forced pass) | no |
| MATCH, k ≥ 1 matches   | 1+k (pass + k matches) | yes (1+k branches) |
| PLAY, 1 card in hand   | 1 (forced discard) | no |
| PLAY, h ≥ 2 cards      | h | yes (h branches) |

### Per-checkpoint deck reshuffle (Part 2)

At every checkpoint, additionally try **N** re-shuffles of the remaining undealt
cards.  Each shuffle becomes an independent deck-ordering sub-tree.

- Total children at a checkpoint with B player options and N reshuffles:
  **B × (N + 1)** (original deck + N shuffled copies).
- N = 0 reduces to Part 1 (fixed deck only).
- For each N, DFS runs until the same node limit is hit.

### Timing

- **Single-pass baseline**: one game with greedy-stingy match + caution play,
  records decisions and checkpoints along that one path.
- **DFS timing**: total wall time until node limit or completion.  Each DFS node
  pays `clone_state` (deep copy) cost.

## Outputs (`artifacts/04/`)

| File | Content |
|------|---------|
| `log.txt` | Per-N summary: node count, terminals, checkpoints, time, limit hit; branch distribution and estimated full-tree size per run. |

## Findings (4p, n_hand=3, seed=42, node\_limit=200k)

### Single-pass baseline
- **1.5 ms** per game.  63 decisions, **47 checkpoints** along the greedy path.

### Part 1: fixed-deck DFS (N=0)
- Node limit hit at 200,000 nodes in **36 s**.
- Per-node cost ≈ 0.18 ms (dominated by `clone_state` deep copy).
- After 200k nodes: 37,336 checkpoints observed, mean branch factor **2.66**.
- Branch distribution: 2→20,791 · 3→9,819 · 4→5,939 · 5→406 · 6→174 · 7→137 · 8→62 · 9→8.
- Estimated full-tree leaves: **10^15,118** — the tree is astronomically large.

### Part 2: N reshuffles per checkpoint

| N | nodes | terminals | checkpoints seen | time (ms) | limit hit |
|---|-------|-----------|------------------|-----------|-----------|
| 0 | 200,000 | 61,966 | 37,336 | 36,425 | yes |
| 1 | 200,000 | 89,417 | 20,899 | 39,445 | yes |
| 2 | 200,000 | 112,893 | 15,463 | 45,764 | yes |
| 3 | 200,000 | 124,015 | 12,051 | 48,391 | yes |

Every run hits the node limit.  Increasing N causes each node to be more
expensive (more child clones per checkpoint), so the DFS traverses fewer
checkpoints before the limit is reached.  Wall time is roughly constant because
it is dominated by the fixed node budget.

### Key conclusions

1. **Exhaustive DFS is completely infeasible** even with a fixed deck.  A single
   4-player game has an estimated tree of **>10^15,000** leaves.

2. **The single-pass greedy path sees 47 checkpoints; the DFS sees 37,000+**
   before exhausting the budget.  Off-policy paths expose vastly more decision
   points than on-policy data collection.

3. **Deck reshuffles add multiplicative branching but do not qualitatively change
   the picture**: the tree is already far beyond exhaustive reach without any
   reshuffling.

4. **Clone cost dominates DFS throughput**.  A deep copy of `RlPick14State` costs
   ~0.18 ms vs ~0.024 ms for a single-pass move application.  Any tractable tree
   search needs either a compact state representation or an incremental undo/redo
   mechanism.

5. **Practical implication**: on-policy rollouts or function approximation (as in
   03-x) are the only viable approaches for this game tree.
