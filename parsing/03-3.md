# Parsing: 03-3 feature-based Q analysis

## Goal

Project the 666k sparse snapshot keys onto a 7-element summary feature vector
so that nearby feature values correlate with similar Q outcomes (N+1 gap).
Then plot mean/quartile/extrema of N+1 gap against each feature.

## The 7 summary features (one per row in the feature matrix)

Each snapshot encodes hand digit-counts and public digit-counts.
We reconstruct:
  hand_list  — multiset of digit values (game_values 1..13) from hand counts
  pub_count  — array of counts indexed by digit-1 (length 13)

For hand_list, all non-empty subset combinations of up to 3 cards give
at most 7 subsets.  Unique subset-sums determine the columns (up to 7).

### f1 — column validness summary
  total_unique_sums / 7
  "How full is the combination space?"

### f2 — unique sum summary
  unique_sums_lt14 / 7   (count of subset-sums strictly < 14)
  "How many partial sums can contribute to a 14-sum match?"

### f3 — known category summary
  count_known_cats / 7
  A sum s is a known category if:  s < 14  AND  (14-s) appears in the public pool.
  "How many distinct digit combos can match right now?"

### f4 — potential category summary
  = f2  (all sums < 14 have a complement in [1,13])
  "How many digit combos could eventually match (given right public draw)?"

### f5 — number of options summary
  - For each *known* category, let **occ** = public count of the complement (game
    value c = 14−s) in the digit vector.  **Per-column value** = `occ / 4` — i.e. a
    linear “how many of four slots” readout, *not* `min(occ, 4) / 4`.  Wording
    like “at most four … normalize by 4 to cap at 1.0” in the original note meant
    “four copies per normal rank in the full deck” as the **scale**, not a clamp.
  - **Implementation:** use the *same* `occ / 4` for *every* complement c — no
    separate code path (e.g. divide by 6) when c is 5.  That is what “no special
    handling of 5” means: not “the situation with five+ copies in the 5-bucket
    is impossible,” but “we do not re-normalize that bucket differently in code.”
  - **When can `occ/4` exceed 1.0?**  For c ≠ 5 the deck has at most four physical
    cards, so (except degenerate / impossible keys) `occ ≤ 4` and the column
    stays ≤ 1.0.  It is a **necessary** condition to get `occ/4 > 1` for a
    category whose complement is **c = 5** and **occ ≥ 5** in public (e.g. 1.25
    if `occ=5`, 1.5 if `occ=6`), because the game_value 5 key counts all six
    5s+jokers.  (Still not sufficient by itself: that category must be "known" in
    the sum.)  We do not clamp.  **Summary** = (sum of column values) / 7, same
    as the other “normalized sum” rows.
  - Early code omitted the /7 and produced bogus highs.  The summary can also
    exceed 1.0 if more than seven known categories contribute or columns exceed 1.

### f6 — max points summary
  max over known_cats of  (best_hand_pts(s) + max_score[14-s]) / 18
  best_hand_pts(s) = max score achievable by hand cards summing to s
                   (using max suit for each digit, careful with duplicates)
  max_score[d]    = highest score_value among all cards of game_value d
  normalization   = 18  (pub Joker 5 + hand Joker 5 + 3H 4 + 1H 4)
  "Best single-match score currently on offer, normalized."

### f7 — second points summary
  max over known_cats of:
    if pub_count[14-s-1] >= 2:  (best_hand_pts(s) + second_max_score[14-s]) / 18
    else:  0
  "Best match score if the top public card is taken by an opponent."

## Scoring table (precomputed from cards.py)

  score_value:  Joker=5, Heart=4, Spade/Blade=3, Diamond=2, Club=1

  max_score[d]:   d==5 → 5 (Joker), all others → 4 (Heart)
  second_max_score[d]: d==5 → 5 (second Joker), all others → 3 (Spade)

  Note: digit 5 has 6 cards: 5C, 5D, 5H, 5S, Red Joker, Black Joker.
  So the top-2 scores for digit 5 are [5, 5], not [5, 4].

## Implementation strategy

1. Build hand config cache (≤560 distinct hand count vectors for n_hand≤3)
   For each config, precompute:
   - unique_sums, unique_sums_lt14
   - best_hand_pts[s] for each s in unique_sums_lt14
   Using this cache, the main 730k-row loop only does cheap lookups + arithmetic.

2. Load 03-1 H1 database (per-key mean_gap, counts).

3. Compute feature matrix (730k × 7) using the cache.

4. For each feature:
   - Bin into 20 equal-width bins over the observed range
   - Weighted percentiles of mean_gap within each bin
     (weight = count; since p50/count=1 most weights are 1)
   - Plot: mean (solid), 25th-75th band (filled), 5th-95th (dashed)

## Outputs  artifacts/03-3/

  features.png   — 2×4 subplot grid (7 panels), gap vs each feature
  log.txt        — feature ranges, bin statistics, key observations
