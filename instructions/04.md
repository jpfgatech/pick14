# Evaluating the Size of the Decision Tree

## Background

Previous data collection of 03-x.md was still on-policy.
As a result the data is rather sparse.
Before we truly decide to simulate by on policy manner
Perhaps we can see how much a brute force costs

## Action Items

Simulate a game, with a fixed deck order
- Whenever there is a decision to be made (among multiple options), mark a checkpoint
- We dive deep all the way into the end of the game, lets say by always taking the first decision
- Then we gradually backtrace to the last checkpoint to test alternative branches
- Finish this 'deck order', and record
- The number of states ever recorded
- The number of checkpoints made
- The distribution of checkpoints based on number of branches
- Importantly, the timing of such a simulation, versus a one pass simulation. Perhaps memory cost as well

Then, consider the case of:
- upon each checkpoint, reshuffle the remaining deck for N times
- Start with N = 1
- Which should create even more checkpoints and branches
- Evaluate how the data scales according to size of N.
- Becareful not to crash the computer. consider keep the simulation size managible, step by step

## Findings

Setup: n_hand=3, seed=42, node limit 200,000.  The script also treats **a single
legal match + pass** as **not** a branch: we always play the match (no
checkpoint there).  Implementation: `scripts/04_decision_tree.py`, details:
`parsing/04.md`.  **Default** run: `--player-counts 4 2` (4p then 2p), fixed deck
only (`--max-reshuffles 0`).

### 4 players

- **Single-path:** 63 decision steps, **39 “real” checkpoints** (excludes
  lone match vs pass), ~1.9 ms.
- **DFS (N=0):** cap hit in **~28 s**; in 200k nodes, **~23,441** checkpoints; mean
  fan-out **3.15**; rough est. 10^**11,348** (order-of-magnitude from branch
  counts).
- Collapsing 1 match + pass **greatly** shrinks the checkpoint count (previously
  ~37k in 200k nodes under the old “branch on any ≥2 moves” rule).

### 2 players (same seed)

- **Single-path:** 61 steps, **39** real checkpoints (coincides with 4p here).
- **DFS:** **~31,794** checkpoints in 200k nodes — **more** than 4p; est. exponent
  **higher** (~10^**14,318** by the same crude product).

So **2p does *not* reduce the decision-tree size** in this test: with two seats,
each player takes more total turns in a full-deck game, the board evolves
differently, and the first 200k explored nodes are **wider** in this sample.

### Conclusions

1. **Exhaustive DFS is still infeasible** even with the match/pass collapse and
   with 2p.
2. **On-policy rollouts or function approximation (03-x)** stay the only realistic
   option.
3. **Clone cost** is the throughput bottleneck.  (Optional N reshuffles: see
   script; not central to the updated numbers.)
