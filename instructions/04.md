# Evaluating the Size of the Decision Tree

## Background

Previous data collection of 03-x.md was still on-policy.
As a result the data is rather sparse.
Before we truly decide to simulate by on policy manner
Perhaps we can see how much a brute force costs

## Action Items

Simulate a game, with a fixed deck order
- Whenever there is a decision to be made (among multiple options), mark a checkpoint
- We dive deep all the way into the end of the game, lets say by always taking the first decision
- Then we gradually backtrace to the last checkpoint to test alternative branches
- Finish this 'deck order', and record
- The number of states ever recorded
- The number of checkpoints made
- The distribution of checkpoints based on number of branches
- Importantly, the timing of such a simulation, versus a one pass simulation. Perhaps memory cost as well

Then, consider the case of:
- upon each checkpoint, reshuffle the remaining deck for N times
- Start with N = 1
- Which should create even more checkpoints and branches
- Evaluate how the data scales according to size of N.
- Becareful not to crash the computer. consider keep the simulation size managible, step by step

## Findings

Setup: 4 players, n_hand=3, seed=42, node limit 200,000 (safety cap).
Implementation: `scripts/04_decision_tree.py`. Details: `parsing/04.md`.

### Single-pass baseline

- **1.5 ms / game**, 63 total decisions, **47 checkpoints** along the greedy path.

### Part 1 — Fixed-deck DFS (no reshuffles)

- Node limit (200k) hit in **36 seconds**.  Deep-copying state costs ~0.18 ms/node
  (≈ 7× slower per step than single-pass).
- In the first 200k nodes: **37,336 checkpoints** seen vs 47 on the greedy path.
  Off-policy paths expose vastly more branching.
- Mean branch factor at checkpoints: **2.66**.
  Branch distribution: 2→20k · 3→9.8k · 4→5.9k · up to 9.
- Estimated full tree: **10^15,000+ leaves** — completely infeasible to exhaust.

### Part 2 — N deck reshuffles per checkpoint

Each reshuffle multiplies the children at each checkpoint by (N+1), so the tree
grows faster but the node budget is hit even sooner:

| N | checkpoints seen | est. tree | time until cap |
|---|-----------------|-----------|----------------|
| 0 | 37,336 | 10^15,118 | 36 s |
| 1 | 20,899 | 10^14,739 | 39 s |
| 2 | 15,463 | 10^13,851 | 46 s |
| 3 | 12,051 | 10^12,405 | 48 s |

All runs hit the cap.  Wall time is roughly constant (node budget dominates).
Reshuffles consume the budget more quickly, leaving fewer checkpoints explored
but each node is wider.

### Conclusions

1. **Exhaustive DFS is infeasible** at any reasonable compute budget for this game.
2. **On-policy rollouts or function approximation** (03-x) are the only tractable
   approach — the 03-x on-policy data is sparse not because the approach is wrong
   but because the game tree is genuinely enormous.
3. **Clone cost** (`copy.deepcopy`) is the DFS bottleneck.  Future search
   approaches would benefit from incremental undo/redo state management.
