## Motivation

We now try to find ways that maximizes the probability of match, while tracking the point gap
Focusing on match number means we are ignoring match quality, i.e. points made
Part of the argument is that the points of a match is dominated by the cards suite
Which is not controlled by player anyhow
Therefore, in the current study we ignore the points as if cards has no suite
(This argument is not fully valid, since upon a match and play decision, the player knows the suite)

## Math Model

We take a snapshot of the game after every match or play action
the snapshot is denoted by an integer vector
there are 13 integers representing the presence of card digit in hand card
e.g. for Joker, 5 of HEART, and 9 of club, we have:
HAND_CARD[5-1] = 2, HAND_CARD[9-1] = 1, counting from zero
similarly for public pool

For each action, we denote the game outcome two rounds into the future

- match or pass by player of round N [snapshot A] 
- (refill after match, if applicable)
- play phase 1, passed, of round N [snapshot B1, if applicable]
- (refill after play phase 1)
- play phase 2, matched, of round N [snapshot B2, if applicable]
- the other players' action phase, symmetric

the exact sequence might differ with current game phase definition
the key is that there are two types of snapshots A/B
and for B there are two variants, based on match or pass outcome

Then for each snapshot, record the outcome of the next two rounds as well:
- snapshotA[N]: number of available match options on turn N+1 and N+2, total points, as well as **point-gap change made from this snapshot baseline** (not total game gap)
- snapshotB1/2[N]: number of available match options on turn N+1 and N+2, total points, as well as **point-gap change made from this snapshot baseline** (not total game gap)

(current policy is that as long as a match option is available player will never pass)

by point gap i mean the point gap realized in the next one or two turn, not full game
E.g. playerA scores 9 points in the turn N+1, playerB 5 points playerC 4 points, in a 3 player game
with average of 6 points, their gap realized is 3, -1 and -2 respectively

in addition to match options, evaluate match catagories as well

by match catagories, evaluate the public card and handset in unique digit combinations
E.g. if there is 8C, 9H, 9D in public card, and AC, 5C, 5D in hand card
- AC + 5C + 8C, AC + 5D + 8C, counted as one catagory. Because we should always choose the most point version, all things equal
- 5C/5D + 9H/9D, count as one catagory as well.
- More options offers more security, whereas catagories offers strategic tradeoff space
- 6C + public 8C versus AC + 5C + public 8C would count as two catagories

keep turn N+1 and turn N+2 separable, so we can analyze for turn N+1 only as well

The state space is enormous and extremely sparse — most exact-state keys appear only once across 20k games. Per-key inference is not meaningful; grouped analysis (03-2) is required.

### Architecture

Data collection is separated from plotting via a trace boundary:
- `simulate_game_trace()` steps the engine and emits compact records only
- `add_trace_to_accumulators()` converts traces to H1/H2 Q-outcome samples
- `AccDB` keeps memory O(unique_keys) via online count/sum/sum-sq accumulators

Snapshots are taken **after** the corresponding action so each key describes the Q-state produced by that action (A after match/pass, B1/B2 after play).

Gap metric = `pts[p, j] − mean_q pts[q, j]` (same turn-index across all players, matching the per-round relative scoring interpretation in the instruction).
